Herald: the right alert, to the right people, with the next step attached

Material for the team's brainstorm on the "Flexible Alerting & Notification Service" brief: who it is for, how it flows, the data schema, the competition, the test cases, and what is already running.

"Herald" is a working name. A skeleton of the service exists and was tested on 20 November, and the web UI now runs against it at http://localhost:8080 once the stack is started. The link below is the earlier prototype with simulated data, which opens anywhere.

One team's tool, or a platform for many?

A platform for many teams. The brief's own examples are three teams (Settlements, Pricing, a Rates trading desk) and one person (Anna), and it names engineers, on-call support and non-engineers as users. That has four consequences for the design.

  • Everything has an owner. Each rule, alert and runbook belongs to a team or a person, and people see only their own.
  • All matching rules fire. One event can matter to several teams at once, so there is no "first match wins".
  • Rules read as plain sentences. A trading-desk user must be able to read "when a rates trade over 10,000,000 is rejected, email the Rates team" and change it.
  • Self-service start. A new team should get its first alert in minutes, from a schema nobody prepared for.

The brief gives three events, four rules and three runbooks, and says judges will bring one more event schema and one more runbook format. Sorting the samples shows what the design must cope with.

Three samples, three places for every basic fact. So Herald assumes no schema: it keeps the payload as it arrived and lets rules read any path.

What the four rules need

  • Exact match, and patterns like pricing-engine-* and trade.rejected.*
  • A number comparison on a nested field (notional > 10,000,000)
  • "WARN or above": severity as an order, across vocabularies
  • AND / OR
  • Grouping: "one alert per instrument every 5 minutes"
  • A title built from event fields; colour; which fields to show
  • "The on-call person", and "SMS between 08:00 and 20:00, otherwise email"

What the three runbooks need

  • Structured YAML, a Markdown list, and a paragraph of free text, all accepted
  • Values from the event filled in ({{workflowId}}, "the instance named in the alert")
  • Steps a person does, and steps the service can run (http_get, retry_workflow, escalate)
  • Conditions written in words ("if one region", "if retry fails twice")
  • Approval: none, required, or "from the team lead"
  • Time: "wait 2 minutes", "every 15 minutes"

How an event becomes an alert

The whole design rests on two transactions. The webhook answers "accepted" only after the broker has the event. A worker moves on only after the alert and its notifications are in the database together. Between those two points an event cannot be lost, and after the second an alert cannot be lost.

The schema to build around

Event

No required fields. The payload is kept untouched.

raw       the payload as it arrived
source    which source it came through
attrs     optional aliases, filled if found:
          @type @severity @timestamp @service

Rules read any dotted path: error.code, payload.notional, data.positions.*.exposure. One line of config per source corrects an alias for a new schema.

Alert and notification

Alert         firing → acked → resolved
  owner, rule, group key, counter
  title, body, fields, colour
  rendered runbook, step state
  person in charge

Notification  pending → sent
  recipient, channel     ↘ retrying → dead
  attempts, next attempt     → next channel
  ingest time, delivered time

Rule: the brief's Rates example, as the service stores it

id: rates-large-trade-rejected
owner: team:rates
when:
  all:
    - {field: meta.schema,      op: glob, value: "trade.rejected.*"}
    - {field: payload.desk,     op: eq,   value: rates}
    - {field: payload.notional, op: gt,   value: 10000000}
present:
  title: "Rejected {{payload.currency}} {{payload.notional}} — {{payload.reason}}"
  colour: amber
group:   {by: [payload.tradeId]}            # same trade again = same alert, counter goes up
notify:
  - {to: team:rates, channels: [email, ui]}

Rules are data, not code: a tree of all / any / not over twelve operators (eq ne gt gte lt lte in contains glob regex exists severity_gte). That makes them safe to accept from a UI, easy to draw as a builder, and able to explain themselves: for any event the service can name the exact condition that failed.

Runbook step: every format ends up as this

text: "Fail traffic over to the other region"
kind: manual                 # check | action | manual | wait
action: null                 # a registered action, or null when a person does it
condition: "one region"      # in the author's words
approval: role:team-lead     # none | required | role:<name>
Runbook handlingWorks onResult
Level 0Anything, even a bare wiki linkShown as written, with event values filled in
Level 1YAML steps, Markdown lists, checklists, sentencesSplit into steps by built-in parsers
Level 2Any prose, with a language model switched onStructured steps with actions proposed, held as "needs review" until a person accepts

An unseen runbook format therefore always produces something useful on the alert. Actions carry a risk level that a runbook cannot lower: a restart, an outbound webhook or an escalation always waits for a second person.

Ideas worth borrowing

  • Alertmanager: group by fields, then wait / interval / repeat timing
  • Keep: the dedup key is something a user can edit
  • Rootly: click a field in a sample payload to use it
  • Sentry: rules as When / If / Then cards
  • PagerDuty: reply codes in the SMS, keypad actions on the call
  • AWS: an approval step with an expiry
  • incident.io: a catalogue of service → team → schedule

Gaps to demo as innovation

  • Bring any schema: fields discovered from the first event, click to build a rule, dry-run on recent events
  • Free-text runbook → steps, with risky steps approved by replying to the SMS
  • "Why didn't it match?" on any event
  • Published, reproducible numbers: few vendors publish throughput or latency at all
  • A postmortem draft from the audit trail

A figure for the pitch: in a 2026 survey of over 1,000 practitioners, 83% said they ignore alerts at least some of the time and 44% had an outage linked to a suppressed or ignored alert (NeuBird, reported by APMdigest, May 2026). It is a vendor survey; say so on the slide.

Security, for a bank

Herald would sit between production systems and people's phones, and it can trigger actions. The threat model has fifteen entries in docs/SECURITY.md, each marked built or not built.

Built and checked

  • Webhooks need a per-source token or a signed, time-stamped request
  • Size and nesting limits on incoming payloads
  • Team scoping on every query; five roles
  • Templates with no logic; values escaped in email
  • Actions cannot reach internal addresses unless allow-listed
  • No shell: actions are typed functions
  • Approval codes: single use, 15 minutes, bound to one approver; the requester cannot approve
  • Audit log that the database refuses to edit, with a hash chain
  • SMS and voice carry a title and a link, not the payload

Not built, and said so

  • Single sign-on: the demo takes identity from headers
  • Verifying the SMS provider's signature on replies
  • Limiting failed approval attempts (matters with 4-digit codes)
  • A rate limit on the webhook
  • Redaction lists and retention limits
  • Encrypted traffic between services, a secret manager
  • Locked dependency versions

The language model

  • Used only while someone is configuring: to structure a runbook, draft a rule, or suggest a field mapping. Never on the event path. Never runs anything.
  • Off by default; everything works without it. The provider is a switch, so a bank points it at its approved private endpoint.
  • It is sent the shape of a schema, not live payloads. What it returns is checked: only registered actions, and it cannot lower an action's risk.
  • Today the checks are written and tested; the call to a provider is not implemented.

The submission must say how AI tools were used. A draft statement is at the end of docs/SECURITY.md. Confirm that sharing the brief with an external tool is within the hackathon rules.

Scaling, and what was measured

  • Nothing in the service holds state. API and workers can be multiplied; rules, dedup, delivery status and audit live in Postgres, events in the broker.
  • Dedup is a database guarantee, one open alert per rule and group key, so it is correct with any number of workers.
  • Single points of failure in the demo: one Postgres, one broker node. Both are replicated products in production.
  • The bottleneck when most events create new alerts is database round trips per alert, not rule matching. Writing each batch in one statement is the next step.

Measured on one laptop (Apple M1 Pro, Docker Desktop with 8 GB), 15 seconds per run at a fixed send rate. Latency is from the event reaching the webhook or broker to the SMS gateway accepting the notification. A run is reported only if every matching event was counted and every notification delivered. A new event schemaNothing. Optionally one mapping line on its source
A new kind of source, operator, channel, runbook format or actionOne small registered function each
A real email or SMS providerReplace the body of one function
  • The core (reading events, matching, routing, templates, runbook parsing, security checks) is pure functions with 84 tests that run in under a second.
  • The brief is the test suite: its four rules against its three events, with the boundaries.
  • The SQL that carries the guarantees sits in one file, each statement commented.

Test cases beyond the brief's samples

All are written out with setup, action and expected result in docs/TEST-SCENARIOS.md, so they can become automated tests or a demo checklist.

Boundaries

  • Notional of exactly 10,000,000 (must not match "over")
  • Notional sent as text
  • Anna at 07:59, 08:00 and 20:00, and in summer time
  • Missing fields; severities spelled WARN, warning, sev2, 4

Schemas not seen before

  • A CloudEvents envelope
  • A real Alertmanager webhook with several alerts in one request
  • A plain-text log line
  • A GitHub-style webhook with the type in a header
  • Lists inside the payload; epoch seconds; numeric severity
  • A deeply nested payment or margin-call event

Runbooks not seen before

  • A checklist with tick boxes
  • Nested numbered steps; a decision table
  • Only a wiki link
  • A shell-script-style runbook
  • A chat message with typos

Failure

  • Kill a worker in the middle of a burst
  • Restart Postgres; restart the broker
  • The same message delivered twice
  • "Resolved" arriving before "failed"
  • Gateway returning errors for two minutes

Security

  • Wrong token; replayed signature; 5 MB payload
  • A payload value containing {{…}} or HTML
  • An action pointed at 169.254.169.254
  • An approval code used twice, by the wrong person, after expiry, or by the requester
  • Reading another team's alerts

Load

  • Sustained rate and burst
  • 1, 2 and 4 workers
  • Few matches against many matches
  • Numbers in the video come from the script, not from estimates

Questions to take to the mentors

  • May the running service call an external language model during judging, or must it work offline?
  • Will the unseen schema be JSON, or could it be XML, a FIX message or plain text?
  • Will judges run it from a fresh clone on their own machine, and with what resources?
